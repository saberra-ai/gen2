## Authoritative cache layout and metadata

Microsoft describes binary caches as packages containing build outputs, integration files, documentation and licenses; source archives are a different asset-cache concern. [Binary cache scope](https://learn.microsoft.com/en-us/vcpkg/users/binarycaching). The **actual tool revision's** [file-provider implementation](https://github.com/microsoft/vcpkg-tool/blob/98d7cb0cf1f4686a3e43aa5672b6230c1d56bce8/src/vcpkg/binarycaching.cpp) stores each ZIP at `<archives>/<first two ABI characters>/<full ABI>.zip` and compresses the package directory. Therefore select exact ABIs from the table, not filename/package-version globbing or whichever cache entry is newest.

Expected package metadata includes root `CONTROL`/`BUILD_INFO`, `share/<port>/vcpkg_abi_info.txt`, `share/<port>/vcpkg.spdx.json` and `share/<port>/copyright`, subject to actual cache inspection. The pinned [build implementation](https://github.com/microsoft/vcpkg-tool/blob/98d7cb0cf1f4686a3e43aa5672b6230c1d56bce8/src/vcpkg/commands.build.cpp) serializes `CONTROL`, computes package ABI as SHA256 of the full raw ABI-info text, and copies that text into the package. Recompute that SHA and require equality with both the retained status ABI and CONTROL ABI. The ABI describes build inputs/configuration; it is **not** a hash of the ZIP or static-library output bytes.

Microsoft's [SPDX documentation](https://learn.microsoft.com/en-us/vcpkg/reference/software-bill-of-materials) describes per-triplet SBOMs, package/ABI identity, port-file checksums and resource origins. Source origins are inferred heuristically from portfile helpers; do not treat them as complete linkage/source attestations. Keep original SPDX JSON rather than losing fields through conversion. The [ABI documentation](https://learn.microsoft.com/en-us/vcpkg/reference/binarycaching#abi-hash) describes configuration inputs and the installed ABI-info file.

The pinned [install algorithm](https://github.com/microsoft/vcpkg-tool/blob/98d7cb0cf1f4686a3e43aa5672b6230c1d56bce8/src/vcpkg/commands.install.cpp) generates `.list` while copying package files, excludes control/manifest/build-info files from installation, adds triplet prefixes and directory trailing slashes, sorts and writes the resulting lines. Consequently **the original installed `.list` need not be in a binary-cache ZIP**. Recovering its body requires either an original retained copy or exact reconstruction from package inventory with this algorithm. Claim original-byte equivalence only after matching the retained size and SHA256, including newline bytes. Otherwise retain it as newly reconstructed metadata and leave the lost-body gap explicit; do not edit the old receipt or rename new metadata as historical.

## Additive recovery job, without native rebuild

1. Restore only the exact existing Actions cache key `nemo-diar-vcpkg-9e593bb18ea69cc5095e012465dcd675a822ed0d-x64-static-md` in a dedicated metadata job **on `refs/heads/codex/nemotron3-platforms`**. The parent's direct GitHub cache listing identifies the sole retained cache as ID `9037586923`, `301702240` bytes, scoped to that branch (last access 09:49 UTC). Ordinary sibling probe-branch restoration cannot assume access: [GitHub cache access restrictions](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache) constrain branch scope. Add a metadata-only collector/workflow on the owning platforms branch; select paths/trigger so the existing native-build workflow does not run. This is future implementation work, not a workflow change performed by this research. Record exact matched key, cache ID/version/scope, job/run/source and Actions restore logs; reject prefix-key fallback. The Actions cache key is a recovery location, not a cryptographic identity of its contents. Never invoke vcpkg install/build as part of recovery, since a miss or changed ABI could build replacement packages.
2. Select the nine exact `<prefix>/<ABI>.zip` entries. Record full ZIP SHA256/size, safe central-directory inventory and metadata-entry hashes. Reject duplicate/unsafe paths, metadata symlinks and ambiguous identity. Read only necessary metadata/notices and static-library identity bytes; do not execute cached tools or install the packages. Retain the original ZIPs in a separately identified evidence artifact if durable receiver re-verification is required, or retain metadata plus a complete entry manifest with a clearly narrower verification claim.
3. Parse CONTROL including port revision, architecture, feature/dependency paragraphs and ABI; match retained status identities/dependency graph without treating `Status:` fields as package content. Rehash raw ABI-info and compare its dependency ABIs. Require target BUILD_INFO to describe static library linkage and dynamic CRT; host/tool metadata can differ. Compare SPDX name/ABI/tool creator and checksum-bearing port files with the matching pinned registry files. Fail missing/mismatched metadata instead of filling historical facts from current defaults.
4. Retain the complete original copyright/notice payloads from all selected packages and compare target-port notices with the exact copies/hashes already installed in the qualified SDK. SDK notice installation paths are recorded separately; do not infer a missing copyright body from a matching upstream license name. Add embedded/header-only source attribution found by the pinned port/source audit where required; SPDX heuristics do not guarantee notice completeness.
5. If `.list` reconstruction is useful, reproduce the pinned algorithm over the original archive inventory and compare **all nine** original size/hash pairs from the provenance JSON. Archive entry ordering, explicit/implicit directories, excluded metadata, symlink treatment, path case and line endings can affect output. Preserve mismatch as a limitation rather than normalizing until a similar list appears.
6. Publish a new recovery receipt binding the original SDK/status/provenance hashes to archive and recovered-entry hashes, source recipes and any exact list-equivalence results. The receiver should be able to independently repeat ZIP selection, ABI hashing, metadata/notice parsing and pinned-source checks. Keep the old receipt unchanged and label the recovery's actual date/source.

## Linkage boundary remains explicit

Cache recovery can establish that a particular ABI-identified package has particular cached metadata, sources/patch declarations, licenses and library bytes, and can bind selected notice/list bytes to the original receipt. It cannot retrospectively prove which `.lib` archive members were selected into an already-built NeMo DLL: installed status is an environment inventory, and ABI metadata is generated before linking NeMo. A retained native linker command/response file, link map or object/member trace tied to the qualified build would strengthen that separate claim; rebuilding a similar SDK or comparing current package names would not recover it. Record the exact available native link evidence and any absence. This additive metadata task closes only what its byte comparisons actually establish; native quality, runtime closure, licensing/entitlement and deployment/coexistence gates remain separate.
