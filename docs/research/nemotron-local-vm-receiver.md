2026-10-17. **Lume has a plausible unattended local route; it is not yet qualified on this host.** Use an Apple restore image, a new guest disk/account and a manually unpacked publisher release. This avoids GitHub authentication/private-app upload and does not require building/signing the VM tool with the host’s keys. Remaining admission checks include actual release trust, restore compatibility/personalization, unprivileged offline-volume access and temporary VNC exposure. No VM tool/archive/OS body was downloaded, installed or executed during this research; only primary source/release metadata and an IPSW HEAD response were acquired. The live neural session was untouched.

## Host and guest effects

Lume’s default install script installs a user LaunchAgent/server; avoid it by manually extracting the versioned command-line archive into a task-private directory. Its release archive contains a wrapper and `lume.app`. The inspected unattended path executes host `hdiutil attach -readwrite -nomount`, `diskutil` mount/unmount, ordinary file writes/chmods inside the **guest Data volume**, then detach. It contains no host sudo, Authorization Services, AppleScript, Keychain or certificate operations. This supports an unprivileged design but does not prove that this locked host’s mount/TCC/session policy permits it without a dialog. Stop and retain a failure if permission is denied; do not escalate. Its later sudo command runs **inside the guest over SSH**, finalizing setup and preboot metadata. [Installer entry](https://github.com/trycua/cua/blob/3350f504014c85416009a90fcb339fe556ce02fc/libs/lume/scripts/install.sh), [offline patcher](https://github.com/trycua/cua/blob/3350f504014c85416009a90fcb339fe556ce02fc/libs/lume/src/Unattended/MacOSOfflineSetupPatcher.swift), [disk commands](https://github.com/trycua/cua/blob/3350f504014c85416009a90fcb339fe556ce02fc/libs/lume/src/Utils/DiskImageSession.swift), [guest finalization](https://github.com/trycua/cua/blob/3350f504014c85416009a90fcb339fe556ce02fc/libs/lume/src/Unattended/UnattendedInstaller.swift).

Unattended Tahoe creates local admin `lume/lume`, SSH, autologin and no-sleep/no-screen-lock settings; it skips Setup Assistant and verifies SSH before stopping. No cloud/Apple/GitHub account appears in this path. This is a vanilla restore **with declared provisioning changes**, not an untouched consumer setup. SIP changes are a separate optional `lume sip` command; neither SIP nor its `vncdotool` dependency is needed for this route. Preserve guest security observations and change guest credentials before private payload use; no host password or signing key is needed. [Pinned README](https://github.com/trycua/cua/blob/3350f504014c85416009a90fcb339fe556ce02fc/libs/lume/README.md), [guest commands](https://cua.ai/docs/lume/reference/cli/guest).

## Alternative: locally built, NAT-only Apple API runner — source audit only

2026-10-17 follow-up. **A VNC-free, profile-free local runner is source-supported as a development design, with host-specific provisioning still unproved.** This is a new qualification artifact, not re-signing either publisher tool or the private app. Only source/document metadata was acquired here, including Apple’s161,642B sample-source ZIP; nothing was compiled, signed, installed or executed.

**Entitlement evidence is concrete.** Apple explicitly says `VZNATNetworkDeviceAttachment` does not require `com.apple.vm.networking`. Apple’s own Containerization Makefile at `6adea5663427b4068108e9268e6125fc139b6045` locally signs `cctl`, its integration tool and `sandboxy` with `codesign --force --sign - --timestamp=none --entitlements=signing/vz.entitlements`; that243B plist contains **only** `com.apple.security.virtualization=true`, SHA256 `5d95521eb14d3cce9af386b484a3c01d767df8681e56d277d999a8f2fa1aa85b`. This is direct Apple source evidence for ad-hoc use of the virtualization entitlement without a certificate/profile, rather than an inference from Lume’s restricted entitlement. Apple documents dash as the ad-hoc pseudo-identity; TN3125 says macOS code without restricted entitlements needs no provisioning profile. An ad-hoc signature supplies local integrity, not publisher identity/notarization, and it is not a promise that every host policy permits execution. [Apple NAT requirement](https://developer.apple.com/documentation/virtualization/vznatnetworkdeviceattachment), [pinned Apple signing commands](https://github.com/apple/containerization/blob/6adea5663427b4068108e9268e6125fc139b6045/Makefile#L336-L337), [exact entitlement](https://github.com/apple/containerization/blob/6adea5663427b4068108e9268e6125fc139b6045/signing/vz.entitlements), [ad-hoc definition](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/RequirementLang/RequirementLang.html), [profile rules](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles).

**Public headless building blocks:** Apple’s `InstallationTool` is Foundation/Virtualization code kept alive with `dispatchMain()`, takes a local IPSW, and has the identical one-key entitlement. It checks `mostFeaturefulSupportedConfiguration` and `hardwareModel.isSupported`, persists disk/hardware-model/machine-ID/auxiliary-storage, validates a configuration, then calls `VZMacOSInstaller.install`. No VNC server or `VZVirtualMachineView` participates in that command-line installation. A proposed runner would retain a normal `VZMacGraphicsDeviceConfiguration` framebuffer as needed by macOS, without creating an AppKit window/view; use `VZVirtualMachine.start`, delegate stop/error callbacks, `requestStop` and bounded `stop` fallback. NAT uses `VZVirtioNetworkDeviceConfiguration.attachment = VZNATNetworkDeviceAttachment()`. Exclude sound devices/host-audio sources, clipboard, bridged/vmnet APIs, private VNC APIs, HTTP server, telemetry and native display loop. This is a proposed adaptation, not a ready Apple headless-run command. [Official Apple sample/API](https://developer.apple.com/documentation/virtualization/running-macos-in-a-virtual-machine-on-apple-silicon), [VM lifecycle](https://developer.apple.com/documentation/virtualization/vzvirtualmachine).

The currently published Apple sample defaults to **macOS27** and includes a new shared-image target. Do not build it unchanged for26.3 or import its DiskImageKit/shared-base additions. Apple’s retrieved API availability metadata places `VZMacOSInstaller`, restore-image, platform, auxiliary-storage, macOS boot-loader and Mac graphics/display configuration classes at macOS12; raw disk-image attachment and NAT are macOS11 APIs. The public building blocks therefore predate26.3; still audit every actual selected overload against the26.3 SDK before a separate build. [Installer availability](https://developer.apple.com/documentation/virtualization/vzmacosinstaller), [Mac graphics availability](https://developer.apple.com/documentation/virtualization/vzmacgraphicsdeviceconfiguration), [raw disk attachment](https://developer.apple.com/documentation/virtualization/vzdiskimagestoragedeviceattachment). Use the established raw `VZDiskImageStorageDeviceAttachment(url:readOnly:)` and macOS boot/platform/installer/NAT APIs. The already HEAD-pinned26.3/25D125 IPSW remains the candidate; actual restore-image requirements, personalization and locked-host execution remain checks. Source zip [published Apple URL](https://docs-assets.developer.apple.com/published/bcec04487547/RunningMacOSInAVirtualMachineOnAppleSilicon.zip), SHA256 `6f59fe7e8e6d8eef98832f4e7b82556707f9a17e1d4c78c0d0b1c3daa8783a15`, includes Apple’s permissive copyright/permission notice; preserve it with any adapted source. ## Installer, no-boot inspector and lifecycle audit — proposed next stage

2026-10-17. The [host-admission receipt/status](</Users/victor/workspace/gen2-nemotron3-n0/docs/research/nemotron-macos-vm-host-admission.md>) now establishes the local one-entitlement helper and blank-APFS prerequisites. It still does not establish restored Data-volume access, IPSW compatibility, a VM or guest execution. This follow-up only reads official Apple SDK26.5 headers/docs and pinned Lume source; it performs no helper/API/build/signing/mount/guest operation.

**The intended no-boot inspector is coherent, with narrow claims.** Load the already hash-verified local IPSW using `VZMacOSRestoreImage.load(from:completionHandler:)`; its callback may run on an arbitrary thread. Record actual OS version/build and local URL, require nonnil `mostFeaturefulSupportedConfiguration` and supported hardware model, and require the selected **4CPU/8GiB** to satisfy both image minima and host bounds. Do not silently enlarge them: the SDK says installing/running below the image minima is undefined. Persist exact hardware-model and fresh machine-ID data. Create new auxiliary storage with that same hardware model and no overwrite option; mismatched platform/auxiliary hardware models are undefined. Preserve disk, model, machine-ID and auxiliary storage together for all future boots. [Restore-image API](https://developer.apple.com/documentation/virtualization/vzmacosrestoreimage), [image requirements](https://developer.apple.com/documentation/virtualization/vzmacosconfigurationrequirements), [auxiliary storage](https://developer.apple.com/documentation/virtualization/vzmacauxiliarystorage).

A fresh sparse RAW100GiB file is107,374,182,400 logical bytes, a multiple of512;8GiB RAM is8,589,934,592 bytes. The SDK explicitly supports RAW creation through file resize/ftruncate. Sparse logical capacity is not a physical-space quota or storage-reserve guarantee. A Mac platform/bootloader, raw block attachment, framebuffer, virtual USB keyboard/pointing and NAT with empty audio devices can be configured and `configuration.validate()` called **without constructing a `VZVirtualMachine`**. The actual selected headers put these basic APIs at macOS11–12, within target26.0/host26.3; do not substitute newer sample APIs just because SDK26.5 contains them. Validation tests runtime configuration/entitlement availability, not restore installation, guest boot, SSH, networking success or an offline installation guarantee. Auxiliary initialization and RAW-file creation are intended output writes despite “no boot.” [RAW attachment](https://developer.apple.com/documentation/virtualization/vzdiskimagestoragedeviceattachment), [configuration validation](https://developer.apple.com/documentation/virtualization/vzvirtualmachineconfiguration/validate()), [NAT entitlement boundary](https://developer.apple.com/documentation/virtualization/vznatnetworkdeviceattachment).

**Installation has a distinct cancellation contract.** After a future protocol separately admits VM creation, keep all VM access on its chosen serial queue; the default initializer uses main queue, compatible with Foundation `dispatchMain()` and no view/VNC/AppKit window. Retain VM, delegate, installer and progress observation strongly for the whole operation; the VM’s delegate property is weak. Construct `VZMacOSInstaller(virtualMachine:restoringFromImageAt:)` on that queue and call `install(completionHandler:)` once, while the VM is stopped. Its completion runs on that same queue. The SDK explicitly makes **VM pause/stop during installation undefined behavior**. Timeout/SIGTERM in the installing phase must instead dispatch `installer.progress.cancel()` after installation has started, then await the installer’s terminal callback within a separately declared cleanup budget. Cancel-before-start and repeated install on the same installer raise exceptions. No API cancellation deadline is documented; no callback within budget remains failure/cleanup-unconfirmed, not permission to call an invalid VM transition. A signal handler must schedule normal queue-based cleanup rather than calling framework methods from raw signal context. [Install contract](https://developer.apple.com/documentation/virtualization/vzmacosinstaller/install(completionhandler:)), [progress cancellation](https://developer.apple.com/documentation/virtualization/vzmacosinstaller/progress), [VM queue/lifecycle](https://developer.apple.com/documentation/virtualization/vzvirtualmachine).

**After installation/normal boot**, `requestStop()` merely requests guest shutdown; success is not proof of exit. Require `guestDidStop(_:)` plus owner-side stopped state for graceful shutdown. A bounded fallback may call `stop(completionHandler:)` only from its supported Running/Paused states; this is destructive, so retain stop completion/error and resulting state rather than claiming a clean guest shutdown. Unexpected `virtualMachine(_:didStopWithError:)` is a failure. Record phase, monotonic timestamps, API request/completion, state transitions, full NSError domain/code/underlying chain and terminal cleanup disposition before releasing the owner. The callback for forced stop, not an assumed guest-shutdown callback, supplies its completion evidence. **Owner death is expected reclamation, not a bounded externally verifiable stop.** Apple DTS recommends relying on Virtualization to clean up after owner crashes, with repeated force-quit/resource-leak testing. Its Apple-Silicon clarification explicitly gives no cleanup timeline and no public persistent/meta handle for a surviving process to confirm a particular guest has finished teardown. Thus kill/reap proves owner termination only. Do not promote a killed-owner timeout to PASS, infer guest death from missing SSH/private helper processes, or kill undocumented framework services. If the owner becomes unresponsive, retain failed/cleanup-unconfirmed evidence and do not automatically mount, reuse or launch a replacement against that disk under a false stopped claim. [DTS architecture advice](https://developer.apple.com/forums/thread/848542), [DTS timing/observability limit](https://developer.apple.com/forums/thread/850709).

**Exclusive disk ownership needs a stronger controller invariant than Lume’s check.** Its pinned `ensureStopped` acquires `flock(LOCK_EX|LOCK_NB)` on the config file and immediately unlocks before attachment: this is a check, not a lock held across patching. A new controller should hold one task-owned exclusive advisory lock across configuration/attachment/VM lifetime and subsequent verified-stop/offline mount/detach; every cooperating phase must use it. Advisory lock release or process exit does not independently prove framework teardown. The inspected VZ attachment header promises no cross-process exclusive-lock guarantee. Bind canonical output paths and disk/model/ID/auxiliary identities; never concurrently attach/mount a running disk, and never substitute a global device-name guess for the established exact-image identity checks. [Pinned Lume lock check](https://github.com/trycua/cua/blob/3350f504014c85416009a90fcb339fe556ce02fc/libs/lume/src/Unattended/MacOSOfflineSetupPatcher.swift#L45-L54).

**Host-network/personalization remains a separate admission question.** Local IPSW parsing is distinct from installation. Apple documents online authorization/personalization for Apple-silicon software updates, but the inspected VZ installer contract does not specify exact26.3 guest-personalization endpoints, a zero-network guarantee, cancellation timing or complete temporary-file placement. Do not infer an offline installer from a local URL or from no guest NIC. Preserve the offline no-boot probe result separately; a future installer protocol must declare/observe its network policy and failures. SDK `VZErrorInstallationRequiresUpdate`10006 is a real failure route: stop rather than install host support updates, request credentials or change host security policy. Likewise10007 installation failure needs its actual underlying evidence, not an assumed signing-server explanation. No private app needs to enter the guest before this setup stage is complete.
