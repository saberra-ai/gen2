# Owned-pool four-versus-three-thread contrast

The [current M1 profile](nemotron-pooled-cpu-profile.md) records a four-thread
default on a three-CPU virtual receiver, RTF 2.37116 and sampled graph-thread
offsets within a barrier counter/yield loop. That supports a controlled thread
contrast; it does not establish a cause or authorize changing production defaults.

The fixed experiment is four fresh processes in order **4, 3, 3, 4**, each on the
same first twelve seconds of the existing qualified AMI smoke audio. Model bytes,
normalized PCM, native geometry, push cadence, segmentation, SDK binaries and
helper executable remain identical across the four calls. Change only the CPU
thread count, which the existing backend manager also supplies to CPU BLAS.
Retain every result, failure, full probability array, turn and process timing.
No outlier selection or additional thread-count search is planned.

The public C ABI does not expose this setting. A new qualification-only C++
helper therefore compiles the exact owned-pool backend/logging implementation
with matching private headers. It does not reuse the old-layout pool helper or
attach a second pool. All 111 selected pristine source/header/patch files are
bound before copying. Apply only the existing owned-pool patch to the copy and
verify every resulting file before compilation; the altered backend source and
private class header must match the qualified profile lock. Reconstruct the
22 public GGML headers from the admitted M1 build archive and its recorded patch
series. Compiler dependency records must admit every used non-system file.

The newly compiled manager implementation is inside the diagnostic executable;
the qualified SDK payloads are unchanged. Results are private-helper behavior,
not public Gen2 performance or a new production runtime. Exact pooled identity,
all 1,200 probability rows/eight channels and all final turns must match the
saved independent public C ABI result before interpreting each timing. Validate
finite, ordered native turn bounds and speaker IDs before any rounding clamp. Preserve
the established 1e-6 bounds and report byte equality separately.

A model-denied preparation phase verifies source and runtime isolation, then
runs two controls of 22 backend lifetimes each: two warm-ups and ten
additional lifetimes at each thread count. The first injects a known error after
the final observation to verify retained partial evidence and a failing exit;
the second must succeed. This synthetic error does not demonstrate leak detection.
Any actual failure records the active phase and all available observations,
including the current attempt, before exiting. It records immediate and settled thread counts, with the prior
two-incidental-worker allowance and at most 100 ms requested settling per
attempt. Model/frontend execution is absent. Strict private-library auditing
still requires the exact 92-image closure. A local `--prepare-only` run on Apple
Silicon must return before asset acquisition or neural admission. The M1 trial
repeats preparation rather than reusing a locally compiled binary.

Neural execution requires the recorded three-CPU M1 receiver and retains
5 GiB/1 GiB free-space floors, a 256 MiB physical reserve, 600-second command
deadlines, process-group cleanup and failure-stop behavior. Bind all imported
local modules before import, committed protocol/source bytes, immutable delivery
archives, protected input inventories before each command and at the end, and
all output JSON/raw descriptors. Deny source/reference/prior-result reads,
protected input writes and network access to the model process. No automatic
retry, parameter tuning, weight change, native SDK rebuild or default selection.

The [protocol](../../tools/nemotron-diarization/macos-cpu-threads.protocol.json)
is committed before preparation/execution. At this preregistration no new helper
has been compiled or executed and no contrast inference has run. Observed timing
will describe this shared VM only. Even a gain would need a separately identified
production implementation and public/lifecycle/long/mixed/quality/package
requalification. Original quality, human timing gold, physical desktop and
release requirements remain unchanged.
